# Agent Proof Runtime Manifesto

**Status:** Product doctrine v0.1  
**Project:** Agent Proof Runtime  
**Principle:** Proof before trust.

---

## 1. Autonomous Systems Need More Than Confidence

AI agents are becoming capable of creating software, modifying files, operating tools, running workflows, and making decisions with limited human supervision.

Their capabilities are growing faster than our ability to verify what they actually did.

An agent may report:

- the task was completed,
- the requested files were created,
- the tests passed,
- the execution followed the required policy,
- no unauthorized action occurred.

But a statement produced by the system that performed the work is not independent evidence that the statement is true.

A successful-looking response is not proof.

A green badge is not proof.

A log generated by the same execution path is not proof.

An artifact without its execution context is not proof.

Agent Proof Runtime exists because autonomous execution requires a stronger foundation than confidence in a model’s final answer.

---

## 2. The Agent Trust Gap

Traditional software is usually evaluated through deterministic inputs, explicit program logic, reproducible tests, and observable infrastructure.

Agentic systems introduce a different operating model.

The path between intention and result may include:

- model interpretation,
- probabilistic decisions,
- tool selection,
- file creation,
- retries,
- partial failures,
- hidden environmental state,
- mutable artifacts,
- dynamically generated plans.

This creates an agent trust gap.

The operator can often see the final result but cannot reliably answer:

- What exactly happened?
- Which inputs influenced the execution?
- Which artifacts were created?
- Were the artifacts modified afterward?
- Which checks were actually performed?
- Can another process independently verify the evidence?
- Is the displayed status derived from evidence or merely reported by the executor?

The purpose of Agent Proof Runtime is not to eliminate uncertainty from AI.

Its purpose is to make execution claims inspectable, portable, and independently verifiable.

---

## 3. Our Core Belief

> Autonomous execution should produce evidence by default.

Every meaningful agent mission should leave behind more than an output.

It should produce an execution receipt containing:

1. the declared mission,
2. the execution events,
3. the resulting artifacts,
4. deterministic acceptance results,
5. cryptographic integrity data,
6. enough information for an independent verifier to reproduce the integrity decision.

The receipt must remain useful outside the original interface and outside the process that executed the mission.

A dashboard may visualize evidence.

It must never become the only place where truth exists.

---

## 4. Proof Before Trust

Agent Proof Runtime follows one primary rule:

> Do not ask the operator to trust a claim that can be independently checked.

This does not mean every real-world fact can be proven cryptographically.

It means the system must clearly separate:

- what was observed,
- what was calculated,
- what was declared,
- what was verified,
- what remains outside the current trust boundary.

The runtime may record that a provider returned an artifact proposal.

It cannot prove that the provider understood the user’s true intention.

The verifier may prove that an artifact matches the hash recorded in the Proof Bundle.

It cannot prove that the artifact is commercially useful.

The acceptance engine may prove that a required file exists and contains a required value.

It cannot replace human judgment about whether the mission should be accepted.

Proof must be precise.

Claims must not exceed evidence.

---

## 5. The Executor Is Not the Final Judge

A system should not be considered trustworthy merely because it validates its own output.

Agent Proof Runtime separates execution from verification.

The runtime is responsible for:

- validating the mission contract,
- invoking the selected provider,
- enforcing artifact policies,
- materializing permitted outputs,
- running deterministic acceptance checks,
- producing the event stream,
- building the Proof Bundle.

The independent verifier is responsible for:

- validating the bundle structure,
- recomputing hashes,
- recomputing the event chain,
- recomputing the Merkle root,
- checking artifact integrity,
- checking critical metadata consistency,
- reporting exact verification failures.

The verifier does not trust a status written by the runtime.

It derives its own result from evidence.

The model does not decide whether the cryptographic proof is valid.

The user interface does not decide whether the proof is valid.

The independent verifier decides whether the available evidence is internally consistent.

---

## 6. Model Output Is Data, Not Authority

Large language models are powerful execution partners.

They are not the root of trust.

A model may:

- interpret a mission,
- propose artifacts,
- generate structured content,
- explain its output,
- assist in planning or implementation.

A model may not:

- authorize itself,
- approve its own execution,
- declare its own evidence cryptographically valid,
- bypass artifact policy,
- redefine acceptance criteria during execution,
- silently expand the mission’s permissions.

The runtime treats model output as untrusted structured input.

Before any proposed artifact is materialized, the runtime must apply explicit policy:

- permitted relative paths,
- file-count limits,
- byte limits,
- allowed artifact types,
- traversal protection,
- symlink protection,
- mission-specific artifact contracts.

Autonomy without boundaries is not reliability.

---

## 7. Mission Contracts Must Be Explicit

Every verifiable execution begins with a declared contract.

The Mission Manifest defines:

- the mission identity,
- the intended goal,
- the selected provider,
- the requested model,
- the permitted artifact surface,
- execution limits,
- deterministic acceptance checks,
- the evidence-retention policy.

The manifest exists to prevent the mission from silently changing during execution.

It answers three fundamental questions:

1. What is the agent expected to produce?
2. What is the agent allowed to affect?
3. How will the result be checked?

A mission that cannot define its boundaries cannot produce a meaningful execution proof.

---

## 8. Logs Are Evidence Inputs, Not Proof by Themselves

Logs are useful.

They help explain sequence, timing, failures, retries, and system behavior.

But logs are mutable data.

A plain event log does not automatically prove:

- that no event was removed,
- that no event was reordered,
- that an artifact still matches the recorded output,
- that critical metadata was not modified,
- that the displayed status was independently recalculated.

Agent Proof Runtime strengthens execution records through:

- canonical serialization,
- SHA-256 hashing,
- chained event hashes,
- RFC 6962-style Merkle construction,
- artifact digests,
- bundle-level integrity hashes,
- independent recomputation.

Cryptographic integrity does not make a claim true.

It makes unauthorized or accidental modification detectable within the declared trust model.

---

## 9. Honest Trust Boundaries

Agent Proof Runtime will not claim security properties it does not provide.

A local process harness is not automatically a secure sandbox.

A Docker container is not automatically protection against hostile code.

A locally verified bundle is not externally anchored.

A hash without an external signature does not provide non-repudiation.

A successful deterministic check does not prove full semantic correctness.

The project uses explicit trust labels:

- `LOCAL_VERIFIED` — the verifier independently confirmed internal consistency and artifact integrity within the local trust boundary.
- `FAILED` — one or more verification requirements did not hold.
- `UNANCHORED` — no independent external transparency service, signature authority, or append-only trust anchor has confirmed the receipt.
- `development-only` — the execution backend is not presented as a production security boundary.

These labels are deliberately conservative.

Trust grows through evidence, not terminology.

---

## 10. The Proof Must Be Portable

The primary evidence artifact is the Proof Bundle.

It must be:

- machine-readable,
- self-describing,
- versioned,
- portable,
- independently verifiable,
- usable without the Mission Control interface.

A user must be able to move the bundle and its referenced artifacts to another environment and run the verifier again.

The ability to verify outside the original runtime is not an additional feature.

It is the core product requirement.

---

## 11. Tampering Must Be Demonstrable

Security and integrity claims should be testable.

Agent Proof Runtime includes a Tamper Lab because users should not have to accept abstract claims about verification.

They should be able to create a disposable copy of a valid run and intentionally modify:

- an artifact,
- an event,
- critical bundle metadata.

The independent verifier should then report `FAILED` and explain the precise reason.

The original run must remain untouched.

A trust mechanism becomes understandable when users can observe both success and failure.

---

## 12. The Human Operator Remains the Final Authority

Verification is not the same as approval.

The runtime may prove that:

- the mission contract was recorded,
- specific artifacts were produced,
- deterministic checks passed,
- the evidence remained internally consistent.

The runtime cannot determine every human value relevant to the mission.

It cannot independently decide whether:

- the result is strategically correct,
- the design is acceptable,
- the business risk is justified,
- the action should be deployed,
- the output should be sent to a customer,
- the consequences are ethically acceptable.

Agent Proof Runtime gives the operator better evidence.

It does not remove the operator from the decision.

---

## 13. Our Non-Negotiable Principles

### Evidence over declarations

Important execution claims must correspond to inspectable evidence.

### Independent verification

The execution path cannot be the sole authority validating its own result.

### Explicit contracts

Mission boundaries, artifact permissions, limits, and acceptance checks must be declared before execution.

### Deterministic judgment where possible

Probabilistic systems may create outputs. Deterministic systems should evaluate objective acceptance conditions.

### Portable proof

The verification artifact must survive outside the original user interface.

### Honest limitations

The system must describe what it verifies and what it does not verify.

### No secret persistence

API keys, credentials, hidden reasoning, and chain-of-thought must not enter logs, reports, artifacts, or Proof Bundles.

### Backward compatibility

New evidence formats must not silently invalidate older receipts.

### Human authority

Evidence informs decisions. It does not seize decision-making power.

---

## 14. What We Are Building

Agent Proof Runtime is being developed as an open execution-evidence layer for agentic systems.

The initial system provides:

- declarative mission specifications,
- deterministic fixture execution,
- optional live model providers,
- controlled artifact materialization,
- deterministic acceptance checks,
- hashed event streams,
- versioned Proof Bundles,
- independent verification,
- Mission Control,
- disposable tamper demonstrations.

The long-term direction may include:

- stronger isolation through gVisor or microVMs,
- enforced network policy,
- external transparency logs,
- signed receipts,
- hardware-backed keys,
- remote attestation,
- standardized interoperability profiles,
- regulated execution policies.

These are roadmap items.

They must not be presented as current guarantees until implemented and validated.

---

## 15. What Success Looks Like

Agent Proof Runtime succeeds when a user can hand an autonomous agent a mission and later receive a portable answer to three questions:

### What was supposed to happen?

Answered by the Mission Manifest.

### What evidence was produced?

Answered by the event stream, artifact records, acceptance evidence, and Proof Bundle.

### Can another process independently verify the integrity of that evidence?

Answered by the independent verifier.

The goal is not to make agents infallible.

The goal is to make their work inspectable.

The goal is not blind trust in autonomous systems.

The goal is accountable autonomy.

---

## 16. Final Declaration

AI agents will increasingly act before a human reviews every individual step.

That transition cannot be built on screenshots, self-reported success, and confidence scores alone.

Autonomous systems need execution contracts.

They need portable receipts.

They need independent verification.

They need trust boundaries that are stated honestly.

They need proof before trust.

**Agent Proof Runtime exists to build that layer.**
